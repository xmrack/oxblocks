Version
{{ version_no }}{% if fcmp_pp %} — FCMP++ (type {{ rct_type }}){% else if rct_type > 0 %} — RingCT type {{ rct_type }}{% endif %}

The first number is the transaction format. Version 1 carried plain amounts that anyone could read, and version 2 hides them with RingCT, which proves that the sums balance without showing them. The second number names the RingCT scheme that hid them. Types 1 and 2 are the original scheme, types 3 and 4 replaced its range proofs with Bulletproofs, type 5 added CLSAG signatures, and type 6 uses Bulletproofs+. Up to type 6, each is smaller and faster to verify than the one before it, and none of them is more private. Type 7 is FCMP++. It keeps RingCT's hidden amounts and Bulletproofs+, and replaces the ring signature with a proof that each input spends one of the outputs in a tree of every spendable output, so it is the first of these to widen the anonymity set. monerod numbers it with the RingCT types although it has no ring. A block reward is public, so a coinbase shows no type at all.

Ring size
{% if coinbase %}—{% else %}{{ ring_size }}{% endif %}

How many outputs each input could have spent. One of them is the real one and the rest are decoys drawn from the chain. Nothing on the chain says which is which. That set is the anonymity set for the input. Consensus fixes the size for everyone, because a transaction that chose its own would stand out. It has been 16 since August 2022. A coinbase creates coins instead of spending them, so it has no ring.

Unlock time
{{ unlock_time }}

The height or time before which these outputs cannot be spent. Almost every transaction sets 0, which means no lock. Consensus locks every coinbase for 60 blocks, so a coinbase reads its own height plus 60.

An optional 32-byte label a sender attaches so the recipient can tell one payment from another. Exchanges used them to match a deposit to an account. This is the plain form, which anyone can read and which makes the transaction stand out. Wallets stopped creating it, so one on a recent transaction is unusual.

Stealth address

Every output is paid to a fresh address used only once. The sender derives it from the recipient's address and a random secret, so the recipient's real address never reaches the chain. Two payments to the same person share nothing an observer can link. The recipient finds the outputs that are theirs by scanning the chain with their view key.

{% if has_view_tags %}
View tag
{% if carrot %}

Three bytes that make scanning cheaper. A wallet has to test every output on the chain to find the ones it can spend, and that test is expensive. The view tag is a cheap first check, drawn from the same shared secret as the stealth address. Carrot widened it from one byte to three, so it now rules out all but one in about 16.7 million outputs before the expensive check runs, where one byte let one in 256 through. It reveals nothing beyond which bucket an output falls in.

{% else %}

One byte that makes scanning cheaper. A wallet has to test every output on the chain to find the ones it can spend, and that test is expensive. The view tag is a cheap first check, drawn from the same shared secret as the stealth address. It rules out 255 of every 256 outputs before the expensive check runs. It arrived in August 2022. It reveals nothing beyond which of the 256 buckets an output falls in.

Janus anchor

Sixteen bytes, encrypted to the recipient. When they decrypt it, the anchor lets their wallet check that the output was built for the address it arrived at. Without that check a sender who knows two of someone's addresses could build an output against one and send it to the other, then wait to see whether the payment is acknowledged, and learn that the two addresses belong to the same person. Carrot added it. To anyone else it is random.

{% endif %} {% if has_unified_ids %}
Unified ID

The output's place in the single sequence of all outputs on the chain, whatever their amount, that the FCMP++ tree is built from. A node finds the output's path through the tree by it, and the path is what a wallet needs to spend the output. It is public: anyone can read it here, and follow it to the path.

Tx_Extra

A free-form byte field that every transaction carries. It normally holds the transaction public key, which the recipient needs to recognise their outputs. From Carrot on, that key is an ephemeral X25519 key rather than an Ed25519 one, in the same place and the same 32 bytes. It can also hold an encrypted payment ID, and on a coinbase the tags a pool or a merge-mining setup adds. Consensus does not require it to parse, so some transactions carry bytes that decode to nothing. Those are shown raw below.
