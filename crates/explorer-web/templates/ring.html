Each input restates its amount under a new mask.

An output's amount is locked in its commitment, a point that hides the amount behind a secret mask. Each input publishes a fresh commitment to the amount it spends, its pseudo-output, under a new mask. For the output really spent, its commitment less the pseudo-output hides no amount at all, only the difference of the two masks, which the sender knows. The next step's signature proves that of one member of the ring{% if decoys %} without saying which, so the pseudo-output carries the real amount without pointing at the output it came from{% endif %}.

C = k·G + a·H

a is the amount, k the output's mask and k̃ a fresh one. H is a second generator with no known relation to G, so no one can open a commitment to two amounts. The output's owner can work out k, so it knows z = k − k̃, and proving that Ci − C̃ = z·G for some member i proves that the pseudo-output holds that member's amount. The sender picks the last input's mask so that the pseudo-outputs' masks add up to the outputs', which step {{ balance }}'s balance needs.

Show me the math {% if cn %}

The ring is P1, …, Pn, and the sender knows x with Ps = x·G for one s. Its key image is

I = x·Hp(Ps)

where Hp hashes a point onto the curve. The signature is two scalars, ci and ri, for each member: 64 bytes a member. The verifier computes

Li = ri·G + ci·Pi
Ri = ri·Hp(Pi) + ci·I

and checks that

Σi ci = Hs(m, L1, R1, …, Ln, Rn)

with m the hash of the transaction's prefix and Hs a hash to a scalar. The sender makes its own Ls = q·G and Rs = q·Hp(Ps) from a random q, picks every other member's pair at random, and computes the hash. It then sets its own cs so that the sum comes out, and rs = q − csx. Only that last step needs x, and every pair looks alike, so nothing says which was the sender's. Rs comes out right only if I was made with the same x, which ties the key image to the output.

{% else if full %}

With k inputs, each column i of the signature holds k + 1 keys: the i-th member of every input's ring, P1,i, …, Pk,i, and

Zi = Σj Cj,i − Σo Co − f·H

the column's input commitments less every output's commitment and the fee f. In the real column the amounts cancel, so Z = z·G, with z the inputs' masks less the outputs', which the sender knows. Each key row has a key image, Ij = xj·Hp(Pj), where Hp hashes a point onto the curve. Starting from a challenge c1, the verifier goes round the columns:

Lj,i = sj,i·G + ci·Pj,i,   Rj,i = sj,i·Hp(Pj,i) + ci·Ij
L′i = s′i·G + ci·Zi
ci+1 = Hs(m, P1,i, L1,i, R1,i, …, Pk,i, Lk,i, Rk,i, Zi, L′i)

and must come back to c1 after the last. Each challenge is a hash of the one before, so the loop closes only where the sender knows every secret of a column: it starts there from random points, goes round, and solves for that column's scalars last. So every input's real member sits at the same place in its ring, which is why wallets used this form only for a single input. The signature is c1 and k + 1 scalars per column, ((k + 1)n + 1) × 32 bytes. m hashes the transaction's prefix, the rest of its RingCT data, which holds the fee, the output commitments and the encrypted amounts, and its range proofs.

{% else if clsag %}

Each member i of the ring brings a key Pi and a commitment Ci. For the real one, P = x·G and C − C̃ = z·G. There are two key images:

I = x·Hp(P),   D = z·Hp(P)

where Hp hashes a point onto the curve. Two hashes of the whole ring, both images and the pseudo-output weigh the two keys into one:

μP = Hs(“CLSAG_agg_0”, P1…Pn, C1…Cn, I, D/8, C̃), and μC the same with “CLSAG_agg_1”
Wi = μP·Pi + μC·(Ci − C̃),   W̃ = μP·I + μC·D

The real member's W is w·G, with w = μPx + μCz, and W̃ = w·Hp(P). Starting from a challenge c1, the verifier goes round the ring over the combined keys:

Li = si·G + ci·Wi
Ri = si·Hp(Pi) + ci·W̃
ci+1 = Hs(“CLSAG_round”, P1…Pn, C1…Cn, C̃, m, Li, Ri)

and must come back to c1 after the last. The loop closes only where the sender knows w. The weights are hashes of the images themselves, so a false I cannot be made up for in D: the proof holds only if both were made with the real member's x and z. The signature is s1, …, sn, c1 and D: (n + 2) × 32 bytes, against (2n + 1) × 32 for an MLSAG. D is stored divided by 8, and the verifier multiplies it back, so it cannot carry a part outside the prime-order group. m hashes the transaction's prefix, the rest of its RingCT data, which holds the fee, the output commitments and the encrypted amounts, and its range proofs.

{% else %}

Each member i of the ring is a column of two keys: Pi, and Zi = Ci − C̃. For the real member, P = x·G and Z = z·G, and the key image is I = x·Hp(P), where Hp hashes a point onto the curve. Starting from a challenge c1, the verifier goes round the ring:

Li = si·G + ci·Pi
Ri = si·Hp(Pi) + ci·I
L′i = s′i·G + ci·Zi
ci+1 = Hs(m, Pi, Li, Ri, Zi, L′i)

and must come back to c1 after the last. Each challenge is a hash of the one before, so the loop closes only where the sender knows both x and z: it starts at its own member from random points, goes round, and solves for its own s and s′ last. The signature is c1 and two scalars per member, (2n + 1) × 32 bytes. m hashes the transaction's prefix, the rest of its RingCT data, which holds the fee, the output commitments{% if base_pseudo %}, the pseudo-outputs{% endif %} and the encrypted amounts, and its range proofs.

The range proof shows each output amount lies in [0, 264). Without it, a negative amount, which wraps around to a huge number, could balance an output worth more than the inputs. {% if let Some(r) = range %}{% if r.name == "Borromean" %}A Borromean range proof writes the amount in 64 bits and commits to each bit apart, C = C0 + … + C63, with Cj committing to 0 or 2j.
